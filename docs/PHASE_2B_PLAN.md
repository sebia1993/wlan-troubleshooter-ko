# Phase 2B 실행 계획 — TShark 필드 호환성 및 프로토콜 인벤토리 기반

## 승인 배경

2026년 9월 3일 사용자는 Phase 2A 병합과 프리뷰 릴리즈 이후 개발을 계속하도록 명시적으로 지시했습니다. Phase 2B는 승인된 Portable TShark를 자동으로 구하거나 저장소에 포함하지 않으면서 실제 프로토콜 인벤토리를 위한 검증 가능한 기반을 준비합니다.

## 이번 단계에서 구현하는 범위

- `tshark -n -G fields` 형식의 필드 카탈로그 파서
- 버전 고정 JSON 추출 프로파일과 중복·미지 키·필드명 검증
- 필수·선택 필드 호환성 해석
- 고정 헤더·탭 구분·이중 따옴표 형식의 fields 출력 파서
- `frame.protocols` 기반 프로토콜 그룹별 프레임 수·첫 프레임·마지막 프레임 집계
- `frame.cap_len`과 `frame.len`을 이용한 잘린 프레임 관찰
- 승인된 필드·필터·패킷 상한만 포함하는 TShark argv 생성
- 기존 빈 격리 디렉터리 정책을 사용하는 실행 전 준비 경계
- 합성 카탈로그·fields 텍스트와 가짜 매니페스트만 사용하는 자동 테스트

## 이번 단계에서 실행하지 않는 범위

- 승인 TShark의 `-G fields` 실제 실행
- 실제 PCAP에 대한 `-T fields` 실행
- IP·MAC·SSID·사용자명·서버 주소 등 식별자 추출
- Raw Payload·쿠키·Authorization·자격 증명·파일 추출
- EAP·RADIUS·DHCP·DNS·ARP·TCP 이벤트 상관분석
- 장애 원인 Finding과 접속 상태 머신
- 자유 입력 Display Filter·필드·옵션
- 실시간·원격 캡처
- TShark 자동 다운로드·업데이트·시스템 설치본 대체

승인된 실행 파일과 DLL이 제공되지 않았으므로 실제 자식 프로세스 경로를 성공한 것처럼 모의하거나 활성화하지 않습니다. 현재 승인된 프로세스 생성은 캡처를 열지 않는 `-n -v` 준비 확인뿐입니다.

## 승인된 메타데이터

Phase 2B 프로파일은 다음 프레임 메타데이터만 허용합니다.

- `frame.number`
- `frame.interface_id` — 선택 필드
- `frame.cap_len`
- `frame.len`
- `frame.protocols`

IP, MAC, 호스트명, SSID, 사용자명, Payload는 프로파일에 포함하지 않습니다.

## 판정 경계

- 프로토콜이 관찰됐다는 사실은 해당 접속 단계의 성공 또는 실패를 의미하지 않습니다.
- 프로토콜이 관찰되지 않았다는 사실은 캡처 위치·시간·방향 때문에 누락됐을 수 있으므로 장애 증거가 아닙니다.
- 프레임 수가 사전 점검 수보다 적으면 일부 결과로 표시합니다.
- 필수 필드가 등록되지 않은 TShark 버전은 호환성 오류로 중단합니다.
- 선택 필드가 없으면 해당 정보만 판단 불가로 표시합니다.

## 자동 검증 완료 기준

- 카탈로그 P·F 레코드와 fields 헤더·행을 엄격히 검증합니다.
- 프로파일 JSON의 중복 키, 미지 필드, 잘못된 식별자와 필드명을 거부합니다.
- 필수 필드 누락 시 프로파일을 해석하지 않습니다.
- 무순서 필드 요청은 승인된 필드 순서로 정규화합니다.
- 이미 만들어진 argv를 검증할 때는 비정규 순서·중복·미승인 필드를 거부합니다.
- 동일한 합성 fields 출력은 동일한 정규화 JSON을 만듭니다.
- 기존 테스트와 Phase 2B 테스트가 Windows CI에서 통과합니다.

## 실제 통합 완료 조건

회사에서 승인한 `tshark.exe`, 필수 DLL, 버전·SHA-256 매니페스트가 제공된 뒤 별도 통합 작업에서 다음을 검증합니다.

- 실제 `-G fields` 호환성
- 실제 캡처의 `-T fields` 출력 형식
- 출력·시간·메모리 제한과 취소
- TShark 종료 후 격리 디렉터리 무잔류
- 네트워크 어댑터 비활성·방화벽 차단 상태

## 다음 단계

승인 TShark 통합 전에는 합성 fields 출력으로 EAP·RADIUS·DHCP·DNS·ARP·TCP 이벤트 스키마와 상관 키를 설계할 수 있습니다. 실제 장애 Finding은 이벤트 정확도와 캡처 한계 테스트가 확보된 이후에 구현합니다.
